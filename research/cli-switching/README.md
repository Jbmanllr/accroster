# How existing tools switch the Claude Code CLI between accounts

Answers [#6](https://github.com/Jbmanllr/claude-account-manager/issues/6) for the map in [#1](https://github.com/Jbmanllr/claude-account-manager/issues/1). Researched 2026-10-24 on macOS against Claude Code CLI 2.1.296. Builds on [research/claude-multi-account](../claude-multi-account/README.md), mainly [02](../claude-multi-account/02-accounts-and-identity.md), [07](../claude-multi-account/07-regrouping-options.md) and [90](../claude-multi-account/90-official-sources.md).

**Labels:** **Docs** = code.claude.com. **CC source** = the bundled JavaScript inside the installed Claude Code 2.1.296 binary, read with `strings` (identifiers are minified; behavior is read from the code, not run). **Tool source** = a switcher's own repository, read through the GitHub API at the commit listed in [Sources](#sources). **Issue** = a user report. **Inference** = my reasoning. No switcher was installed or run, and no credential was read.

## Answer

- **Swapping the default Keychain item and `oauthAccount` (CCSwitcher, claude-swap, clauth's global switch, caam, aisw) moves Sessions that are already running.** Claude Code re-reads its credential store while it runs. Its Keychain cache lasts 30 s. It rechecks the store when its token is unusable, when it refreshes and on 401s. It also has a "sibling-login watch" that adopts a login another process wrote (CC source). The tools say the same thing: CCSwitcher says a session's "next API call will use the freshly-swapped credentials". claude-swap says a running session "picks up the switch once that cache expires". clauth logged two busy sessions that kept spending the old account until it changed its write order. aisw's claim that a running process keeps its account does not match the code.
- **One `CLAUDE_CONFIG_DIR` per Profile, picked at launch by a shim that reads a pointer file (claude-switch, swapdex), is the only surveyed mechanism that meets all three criteria.** On macOS Claude Code keys the Keychain item to the directory: `Claude Code-credentials-<first 8 hex of sha256(dir)>` (CC source). A switch then only rewrites the pointer. It never writes a credential, so a running Session's item and environment stay as they were. Transcripts stay shared only when the Profile directory symlinks `projects/` back to `~/.claude/projects`. ccsw, swapdex and clauth do this; claude-switch and claude-account-switch do not.
- **Per-shell wrappers (the documented alias, `ccsw <name>`, `cswap run`, `clauth start`) are the same mechanism without a pointer.** They fit the per-shell override on the map's nice-to-have list.
- **Local proxies that route each request (swapdex `serve`, clauth's gateway, CC Switch routing) move running Sessions on purpose.** They fail the map's rule that running Sessions never change Profile.
- **Anthropic shipped no multi-profile switcher for the CLI in 2026.** The docs still prescribe one `CLAUDE_CONFIG_DIR` per account. #30031 and #89993 remain open. The VS Code extension gained a "Switch account" screen (2.1.268 to 2.1.285), which is a sign-out and sign-in flow, not stored profiles.

## How Claude Code 2.1.296 finds and reloads its login (CC source)

| Fact | Evidence |
|---|---|
| Keychain service name | `"Claude Code" + OAUTH_FILE_SUFFIX + "-credentials" + suffix`. Suffix is empty when `CLAUDE_CONFIG_DIR` is **unset**, else `-` + first 8 hex chars of `sha256(configDir)`. Account = `$USER`. Read via `/usr/bin/security find-generic-password`. |
| Hash input is the raw env string | Config dir = `(CLAUDE_CONFIG_DIR ?? ~/.claude).normalize("NFC")`. There is no `realpath` and no `~` expansion, so `CLAUDE_CONFIG_DIR=$HOME/.claude` selects a **different** item from the unset default. A trailing slash or a symlinked path changes the item too. clauth's comment that Claude Code "resolves symlinks before hashing" does not match this function. |
| Plaintext fallback | `<secure-storage dir>/.credentials.json`, the same directory as the config dir unless overridden (below). Matches the [docs](https://code.claude.com/docs/en/authentication#credential-management). |
| Undocumented override | `CLAUDE_SECURESTORAGE_CONFIG_DIR` picks the Keychain item and fallback file separately from the config dir. It is set to an empty value when spawning teammates and is listed among env vars passed to background sessions. It does not appear on the [env-vars page](https://code.claude.com/docs/en/env-vars). |
| Keychain cache | Reads are cached for 30 000 ms (`j0t=30000`). The changelog confirms "macOS keychain cache extended from 5s to 30s" (2.1.86). |
| Reload triggers | (a) The `.credentials.json` mtime changed, or the file is missing (the usual macOS case). Either way it re-reads the store and, if the access token differs, emits `credentialsChangedOnDisk`. (b) The in-memory token is unusable: it rechecks at most every 30 s. (c) Every refresh attempt calls the same check before reading the store. (d) 401 handlers re-read the store. |
| Sibling-login adoption | `_startSiblingLoginWatch` subscribes to `credentialsChangedOnDisk` and runs `_adoptSiblingLogin` (telemetry event `auth_sibling_login_adopt`), behind flag `tengu_streamed_thimble`, which defaults to on. A running Session therefore takes on a login another process writes into **its** store. |

Inference: the item a running Session reads is fixed by its environment at exec time (`CLAUDE_CONFIG_DIR`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`). Anything that writes a new login into that item moves the Session. Anything that only changes which item **future** processes use leaves it alone.

[90-official-sources](../claude-multi-account/90-official-sources.md) called the item name UNVERIFIED and cited #20553 ("OAuth credentials shared across CLAUDE_CONFIG_DIR profiles", still open, last updated 2026-02-26). The 2.1.296 code namespaces the item whenever `CLAUDE_CONFIG_DIR` is set, so #20553 probably describes older behavior. That was not tested on a live login here.

### Reported breakage

- **The swap races the refresh and spends the wrong account.** clauth wrote the Keychain item after relinking `.credentials.json`. During that window a busy Session reloaded the old login and "stayed on the account the switch left for the rest of its life (2026-09-24: two busy sessions kept spending a 5h-spent account)". It now writes the item first (clauth `src/claude.rs`, `keychain_mirror_source`).
- **Refresh tokens are single-use.** Two holders of one login revoke each other. swapdex documents "one such split cost a scheduled job 42 hours" and refuses a snapshot switch while a Session runs on that login. clauth says "a double-spend costs the loser one rejected request". claude-swap refuses to activate a backup that has fallen behind a running Session.
- **A write replaces the whole Keychain item.** The item holds `claudeAiOauth`, `mcpOAuth` and other keys. A naive swap signs the user out of every MCP server (clauth `src/keychain.rs`). The changelog fixed a related Claude Code bug in 2.1.281: "credential writes dropping stored MCP OAuth tokens … when the login keychain was locked".
- **A stale `oauthAccount` never corrects itself.** Claude Code trusts the cached identity in `.claude.json`. A shared or stale block shows the wrong account and organization, so clauth strips it on every switch and swapdex keeps the file per slot.
- **Shared plugin indexes break.** `installed_plugins.json` and `known_marketplaces.json` hold absolute config-dir paths, so one shared index is valid for only one directory (ccsw README).
- **Moving a config dir orphans its login.** The item name hashes the path (#89993; CC source).
- **Desktop overwrites the default item.** Desktop's bundled Claude Code writes the bare `Claude Code-credentials` item and replaces the terminal login (#101990, open).
- **The old account keeps getting charged.** #102447 (open, 2026-10-15, CLI 2.1.300): after `/logout` then `/login` in a running Session, usage looked charged to the new account as if old state persisted. Cause unconfirmed.
- **Transcripts can disappear from `--resume`.** swapdex: kept per slot, "every conversation started on A vanish[ed] from `claude --resume`". clauth: a Session whose `settings.json` is empty would apply the default `cleanupPeriodDays` to a shared `projects/`. Inference: every Profile that shares `projects/` must share the same `settings.json`, or at least the same retention.

## Mechanisms against the map's criteria

| Mechanism | Global for new `claude` runs | Running Sessions untouched | Transcripts shared | Safety bar |
|---|:-:|:-:|:-:|---|
| **A.** Swap the default Keychain item + `oauthAccount` | ✓ | **✗** (30 s cache, refresh and 401 rereads, sibling-login adoption) | ✓ | Fails (1) in most tools, whose token copies sit in plaintext stores (clauth `~/.clauth`, swapdex `~/.local/share/swapdex`). CCSwitcher and claude-swap keep copies in the Keychain. Rewrites the undocumented `~/.claude.json` while Claude may be running, which strains (3). |
| **B.** Per-Profile `CLAUDE_CONFIG_DIR`, chosen at launch by a PATH shim reading a pointer | ✓ (for anything that resolves `claude` through `PATH`) | ✓ (env fixed at exec; switch writes no credential) | ✓ only with `projects/` symlinked to `~/.claude/projects` | Passes. Each Login is made by Claude Code's own `claude auth login` into that Profile's own Keychain item, so the app never copies a token to switch. Writes go only to the app's own files: pointer, shim, Profile dirs, symlinks, a seeded `.claude.json` copy. `~/.claude` is not modified. |
| **C.** Per-shell wrapper (alias, `ccsw`, `cswap run`, `clauth start`) | ✗ (per shell) | ✓ | depends on links | As B |
| **D.** Local routing proxy (`ANTHROPIC_BASE_URL`) | ✓ | **✗** (moves them per request) | ✓ | Tokens held in a plaintext store and replayed by our process (swapdex); a large surface |
| **E.** `CLAUDE_SECURESTORAGE_CONFIG_DIR` per Profile, config dir left at `~/.claude` | ✓ via shim | ✓ (inference) | ✓ (nothing split) | Undocumented internal variable. The shared `~/.claude.json` `oauthAccount` would describe only one Profile. Needs a spike before use. |
| **F.** `CLAUDE_CODE_OAUTH_TOKEN` injected per run | ✓ via shim | ✓ | ✓ | Fails (1): the token leaves the Keychain into the environment |

**Only B meets all four.** C is B's per-shell variant, the map's nice-to-have.

## What B implies for the spec

These are inferences, built from the evidence above.

1. **Make it global with a PATH shim, not by rewriting state.** Place a `claude` shim in a directory ahead of `~/.local/bin` on `PATH`. It sets `CLAUDE_CONFIG_DIR` from the app's pointer only when the variable is unset (swapdex's rule, which keeps a per-shell override possible), then `exec`s the real binary. Do not replace `~/.local/bin/claude`: the installer manages that symlink. A shell function (claude-account-switch) misses scripts and non-interactive shells. `launchctl setenv` misses shells that are already open.
2. **Pass the directory as one fixed absolute string,** with no trailing slash and no symlinked path, because the Keychain item name hashes the raw value. Decide whether the default Profile keeps the bare item (leave `CLAUDE_CONFIG_DIR` unset). If it does, Desktop's bundled Claude Code can overwrite it (#101990). The safer option is to give every CLI Profile its own directory and leave the bare item to Desktop.
3. **Link everything shareable back to `~/.claude`.** That covers `projects/`, `settings.json` (needed for one `cleanupPeriodDays`), `CLAUDE.md`, `skills/`, `agents/`, `commands/`, `rules/`, `hooks/`, `keybindings.json`, `history.jsonl`, `plans/`, `todos/` and caches. Keep per Profile: the Keychain item and `.credentials.json` fallback, `.claude.json` (a copy seeded without `oauthAccount`), and the two plugin index files with their paths rewritten for that Profile.
4. **The costs to accept or engineer around:**
   - `.claude.json` holds user-scope MCP servers, project trust and global config keys. Per Profile, these drift. clauth runs a background syncer, claude-swap mirrors `mcpServers`, and ccsw copies once at `add`.
   - MCP OAuth logins live in each Profile's Keychain item, so they are per Profile.
   - Desktop and the VS Code extension bypass the shim. The extension reads `claudeCode.environmentVariables`, and Desktop reads `CLAUDE_CONFIG_DIR` only at launch.
5. **Adding a Profile** = create the directory and links, then run `claude auth login` with that `CLAUDE_CONFIG_DIR` (claude-switch and swapdex do this). That matches the map's "one browser sign-in started from the tray".

## Open questions

- Should `sessions/` (the registry of running processes) be shared? ccsw keeps it per Profile; clauth links it. If shared, `claude agents` and peer discovery see every Profile's Sessions; check the effect of mixing.
- Is E (`CLAUDE_SECURESTORAGE_CONFIG_DIR`) stable, and which other state is read from the config dir rather than from the token? It could remove the `.claude.json` split, but it is undocumented.
- Does a Session started through B ever write the base `~/.claude/.claude.json`? Expected not, since the config dir moves it. Not tested.
- Does #20553 still reproduce on 2.1.296? The code says no. Not tested against a live login.
