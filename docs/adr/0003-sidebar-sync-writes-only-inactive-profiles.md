# Sidebar sync copies entries into inactive Profiles only, and never deletes

Sidebar sync copies each existing Sidebar entry (`local_*.json`) into every other Profile folder under `claude-code-sessions/`. While the desktop app runs, it writes only to Profiles that are not the desktop's Active Profile: the app keeps no memory of those folders and reads the target folder fresh from disk on an account switch, so a copy written before the switch is picked up. The active Profile's own folder is written only by the app, and by sync only when the app is not running. Automatic mode mirrors the active Profile's folder shortly after each change; Manual mode is a "Sync now" button. Sync never needs to quit the desktop app. The setting defaults to Off.

## Considered Options

- **The official route only** (`claude --desktop --resume <id>`). Kept for opening a Session that has no entry in the Active Profile, but rejected as the sync mechanism: one Session at a time, a fresh entry with no title or archive state.
- **Sync with the app quit** ("Quit Claude, sync, reopen", or on quit). Rejected once the code showed inactive folders are safe to write: quitting interrupts any desktop turn in progress.
- **Creating entries for CLI-only Sessions.** Rejected: it means guessing at fields the app may later depend on; copying a real entry is what existing tools already do without reported problems.
- **Propagating deletes.** Rejected: the app refuses to reap a Transcript while another Profile holds an entry for it, so a propagated delete would strip that protection and let one click destroy the shared Transcript.

## Consequences

- A copy keeps the file name, `sessionId` and `cliSessionId`, and clears `bridgeSessionIds` and the connector snapshot (`remoteMcpServersConfig`, `enabledMcpTools`). WSL and scheduled-task entries are skipped. SSH and No-folder (scratch-workspace) entries are copied unless the user turns off "Include SSH and No-folder Sessions" (on by default); see the amendments below.
- Skipping stays strict but is reported: each run's result says how many Sessions it left out and why, in plain words ("left out 2 scheduled-task Sessions (Claude runs those on one account only)"), and a run writes one sidebar at a time so the menu and Settings show its progress.
- A `deleted_*` tombstone only stops sync re-adding that Session to that Profile.
- Entries carry no per-field timestamps, so sync keeps its own record of each copy's title and archive state as of the last run; a copy that differs from the record changed and wins. If two changed, the active Profile's copy wins, else the newest file.
- If the desktop app's dormant multi-account mode is ever enabled, inactive Profiles may be written in the background: sync detects it, stops and warns.
- Every write follows the safety bar: backup, temp file then rename, abort on unknown files.
- While the desktop app runs, sync leaves alone every Organization folder of the desktop's account, not only the Active Profile's. The app records the active account (`lastKnownAccountUuid`) but not the active Organization, and guessing it from the newest-written folder could be wrong, so a wrong guess would mean writing the folder the app is using. The cost: a Login's other Organizations only sync once Claude is quit or switched to another account.
- The dormant multi-account mode's second proxy, "a target folder changed since sync's own record", is narrowed to: a folder sync may write, of an account other than the one the desktop used at the last run, whose copies changed since that run, with no account switch in between (the desktop's folder unchanged and no `Login-state transition` line in `main.log` since; a shorter log counts as a switch). Taken literally, every account switch and every edit in the desktop's own folder would also pause sync, so the literal proxy pauses on ordinary use. The exact file is still read again right before it is replaced, and any difference from the plan pauses sync.

## Amendment: SSH Sessions are included

The owner's first real switch left out 17 desktop SSH Sessions (entries with `sshConfig`, `sshRemoteTranscriptPath` or `sshRemoteProcessId`), which made sync look broken. They are now copied by default, with the same field clearing, backups and conflict rules as local entries; Settings › Sidebar sync has an "Include SSH Sessions" checkbox to leave them out. A copy also drops `sshReattach`: it binds the Session's remote process to the login that started it, so a copy under another login must not claim it. How a copy behaves when opened under another login is not verified yet, so the app says nothing about it. WSL and scheduled-task Sessions stay skipped; No-folder Sessions are included since the amendment below.

## Amendment: No-folder Sessions are included

The owner didn't understand why the result line left out "scratch" Sessions "(not synced: they belong to one desktop login)", and wanted them synced. Those are the desktop's "No folder" Sessions: their working folder is a scratch workspace Claude made under `~/Library/Application Support/Claude/scratch-workspaces/<account>/<org>/<id>`. They are now copied by default under the same rules as other entries (backup, field clearing, additions only into the sidebar Claude is using while it runs). The scratch workspace stays where it is and the copy keeps pointing at it. One Settings checkbox, "Include SSH and No-folder Sessions" (replacing "Include SSH Sessions", on by default), leaves both kinds out. The "belong to one desktop login" wording is gone: what is left out is said with its reason, "left out 2 scheduled-task Sessions (Claude runs those on one account only)" for WSL and scheduled-task Sessions, "(Include SSH and No-folder Sessions is off)" for the others.

## Amendment: Claude's own sidebar gains new entries while it runs

After real use, the owner wants to sync whenever they choose, without quitting Claude. While the desktop app runs, the folders of its account are no longer left alone: they get additions only. Each Session entry such a folder lacks is copied in as a new `local_*.json`, with the same clearing, `sshReattach` drop, backup and timestamps as any copy. An entry already in one of those folders is never replaced (Claude may be saving it from memory), and a new file is linked into place only if no file took its name meanwhile, so an entry Claude writes first wins. The desktop app doesn't watch the folder; it reads it at launch or on an account switch, so the result line says how many were added and that Claude shows them once it's reopened, and how many changed entries there wait until Claude is quit. When Claude isn't running, sync is unchanged. When it runs on an account that can't be read, nothing is written, as before. Sync's record holds its own additions, so neither the watch nor the pre-write check takes them for the dormant multi-account mode.

## Amendment: Reopen Claude shows the added Sessions

The added Sessions only show once Claude reads its folders again, at launch or on an account switch, so the owner asked for a button rather than quitting Claude by hand. After a run that added at least one entry to a folder of the account Claude is using while it runs, the menu's result line and Settings › Sidebar sync offer **Reopen Claude**. It runs the Guided switch's busy guard first: when Claude is idle it asks Claude to quit the way ⌘Q does (never a force quit), waits for it to exit, then opens it again. While a desktop turn runs it waits, naming the Sessions, and re-checks each tick until they are idle (Cancel leaves Claude alone). When the guard can't tell, it asks: Reopen anyway or Cancel. Claude still running 30 seconds after the quit request is reported ("Claude didn't quit · try ⌘Q in Claude") and the button is offered again; nothing is opened. Automatic sync waits while Claude quits and opens.

This replaces the rule that no code path quits or relaunches Claude: AccRoster quits and relaunches Claude only when the user clicks Reopen Claude, and only once Claude is idle or the user chose Reopen anyway. Sync itself still never quits Claude, Automatic sync never reopens it on its own, and the Guided switch only brings it forward.
